# ReqPub security whitepaper

Two pages for a security reviewer deciding whether this belongs in their
environment. Every claim here is tied to an artifact in the repository and a
test that demonstrates it; the mapping is machine-checked by
`tools/claims-gate.mjs` on every build.

## What ReqPub is

A neutral acceptance record layer for professional services. Agents and people
propose, and a human accepts. Every accepted baseline is fingerprinted, can be
signed and sealed, and can be verified by a third party without ReqPub taking
part.

## What it is not

ReqPub calls no model API. There is no inference in the product, and the claim
is enforced by grep across every source tree on every build. The intake mapper
is deterministic. Nothing enters a record without a person approving it.

ReqPub asserts no judgment about the work it records. No score, no status, no
health, no ranking. This is a design constraint, not an omission, and the tests
refuse copy that would imply otherwise.

## Architecture in one paragraph

A static application shell talks to a managed PostgreSQL database through
row-level security and definer functions; sensitive writes never happen as raw
table access. Signing happens in an isolated function whose private keys exist
only as function secrets. Files live in a private object store reached only
through short-lived signed URLs. Two independent RFC 3161 authorities timestamp
each receipt. The only agent-facing surface is a read-mostly MCP endpoint.

## The controls a reviewer will ask about

**Access control.** Every table carries row-level security. Every function in
the public schema is private unless it appears in a committed allowlist;
`docs/security/AUTHZ_MATRIX.md` is regenerated by a test on every build and drift fails the
build. Seventeen functions are reachable without a session, each gated by a
single-purpose token inside its own body.

**Token model.** Sign, share, update, reply, and request links each carry a
single-purpose token. A token opens exactly one surface: all twenty cross pairs
are tested and refused. No token value appears in any export, receipt, pack,
payload, or log. A revoked token is byte-indistinguishable from one that never
existed, so revocation is not an enumeration oracle.

**Integrity.** Activity and receipt tables accept inserts and refuse updates
and deletes by policy and trigger. Each activity row links to the previous
row's hash; rewriting history breaks the chain at the exact seam and
verification names the divergence.

**Cryptography.** SHA-256 over canonical JSON with sorted keys, one recipe
implemented identically in the application, the public verify page, and a
standalone CLI, with byte-equality enforced in CI. Ed25519 signatures over
receipts, with public keys published at a stable URL and pinned by key id. Two
independent timestamp authorities per seal, with the receipt stating honestly
which responded.

**Egress.** Webhook destinations must be public hostnames. IP literals in every
notation, userinfo disguises, internal suffixes, single-label names, and
trailing-dot forms are refused at creation and again at dispatch. Redirects are
not followed. The stated residual is DNS rebinding, which is in scope for the
penetration test.

**Agent surface.** Five read tools and one write tool that files an ordinary
inbox item for human triage, doubly gated per key and per project, both
defaulting off. Rate limited per key with parallel-load verification. A refusal
for a foreign project is indistinguishable from a refusal for one that does not
exist.

## Offline verification, the ten-minute test

A buyer's security team can verify a ReqPub record without an account,
without network access to ReqPub, and without trusting anything ReqPub says.
The walkthrough is in `VENDOR_PACK/OFFLINE_VERIFICATION.md`.

## What is not yet done

Stated plainly because a whitepaper that omits this is not worth reading:

- Third-party penetration test: not yet commissioned. OWNER ITEM O1.
- Third-party cryptographic review: not yet commissioned. OWNER ITEM O2.
- SOC 2 Type I: not yet engaged. OWNER ITEM O2.
- Storage-probing adversarial suite: not yet written, C1.6.
- DNS rebinding on webhook delivery: accepted residual, C1-005.

The in-house adversarial sweep found and fixed two serious defects before any
external party looked, both documented with reproductions in
`docs/security/HARDENING_REPORT.md`. That report is included in this pack deliberately: a
vendor who shows you only clean results is showing you an incomplete search.
