# Identity and access

The question an identity team asks first, answered on one page, leading with
what is missing.

## What is not available today

**No SAML. No OIDC federation. No SCIM provisioning. No ReqPub-enforced MFA.**

Authentication for the accounts that exist is delegated to the hosting
provider's auth service. SAML is a configuration on that provider's enterprise
tier rather than a build here, and it will be enabled for the first customer
who requires it as a condition of signature. It is stated first so nobody has
to discover it in a questionnaire.

## Who holds an account

| Role | Account | Provisioned by | Access ends when |
| --- | --- | --- | --- |
| Manager | Yes | Invitation from an existing manager | A manager removes them, or the invitation is revoked before first sign-in |
| Viewer | Yes | Invitation from a manager | Same |
| Client sponsor or approver | **No** | A single-purpose signing link | The link is revoked, or the signature is complete |
| Subject matter expert | **No** | A single-purpose workspace link | The link is revoked |
| Update recipient | **No** | A single-purpose thread link | The link is revoked |
| Agent | **No** | An MCP key issued by a manager | The key is revoked |

## Why the signing surface is not federated

The people who sign hold no accounts. That is a design decision, not a gap.

A client sponsor approving a baseline, a subject matter expert answering a
question, and a recipient replying to an update all act through a token that
opens exactly one surface. There are five token types. All twenty cross-pairs
are refused, and `tests/backend-e2e/token-injection.test.mjs` proves it on
every build. A revoked token is byte-indistinguishable from one that never
existed, so revocation leaks nothing about what used to be there.

The operational consequence is the part worth reading twice: **when an employee
at your firm or your client leaves, there is no ReqPub account to
deprovision, because there never was one.** No orphaned seat, no forgotten
licence, no quarterly access review of people who signed something once. Any
outstanding link is revoked individually and immediately.

That is a better answer to the deprovisioning question than SAML would be, and
it is true today.

## Controls that exist for the accounts that do exist

Invitation only. There is no self-service path into an existing organization.
Role is assigned by an existing manager. Every write carries a server-stamped
identity that the client cannot choose. Every table carries row-level
security, and the entire executable surface is enumerated in
`docs/security/AUTHZ_MATRIX.md`, regenerated by a test on every build.

An organization-level email domain allowlist is **not implemented**. If your
security review requires that membership be restricted to a domain you
control, say so and it becomes an idempotent migration rather than a
negotiation.

## Sessions

Session lifetime, refresh behaviour, and password reset follow the hosting
provider's auth configuration. The exact values in effect are available on
request and are not restated here, because a number copied into a document is
a number that drifts.

## The question behind the question

Most identity reviews are asking two things: who can see our data, and how
does access end.

Who can see it: only members of the organization that owns the record,
enforced in the database on every read and write, tested from a rival
organization's account in every backend suite.

How access ends: an account is removed by a manager. A link is revoked and
immediately stops working, indistinguishably from one that never existed.
Neither depends on us noticing.
