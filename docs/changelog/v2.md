## 2.57.9 · The build goes green, and the reason it was red

Freeze release. Continuous integration was failing on main across eight
consecutive runs. Every failure traces to three defects introduced with the
gates themselves, all of them here.

**Ordering.** The workflow installed dependencies near the end, after the
suites and after the step that records what the suites prove. On a clean
runner both chains failed for want of node_modules. Locally everything passed,
because node_modules was already there. The gates were only ever exercised on
a machine that already had what they needed.

**A recorder that lied quietly.** When a chain failed, record-counts warned,
carried on, and wrote whatever partial output it had seen: 415 checks instead
of 1,392. The claims gate then compared the website against that number and
failed the build for a mismatch it had been handed. A script that reports a
count from an unfinished run is worse than one that crashes. It now echoes the
suite output so a failure is readable in the log, and exits non-zero rather
than recording anything.

**A staleness check that could never pass in CI.** The claims gate compared
the recorded time against the modification times of the test files. A git
checkout stamps every file with the checkout time, so on any clean runner every
test looks newer than every record. The check would have blocked every build
while passing on every laptop, which is the worst arrangement available.
Staleness is now a content hash over the suites, which answers the honest
question: are these the tests that produced these numbers. Proven by editing a
suite and watching the gate name both hashes.

The workflow was rebuilt around fail-fast ordering: dependencies, then the
static gates that take seconds, then the suites once, then the gates that read
what the suites produced. It gained a concurrency group so a superseded run
cancels, a timeout, npm caching, and a final step that fails if the committed
counts are not the counts the suites just produced.

Also: engines now declares a Node floor of 20.11 rather than leaving it to be
discovered, and npm run ci runs the exact CI sequence locally, so a reviewer
can reproduce the build with one command instead of reading a YAML file.

Verified by simulating a clean runner end to end: a copy of the repository with
no node_modules and every file stamped at checkout time, npm ci, then all
thirteen steps in order. All pass, 1,392 checks, and the committed counts match
what the runner produced byte for byte.

Deploy: no SQL, no function redeploys. Push; hard refresh.

## 2.57.8 · The session client comes home, the gates go into CI, and the site says true things

Freeze release. One high-severity fix, four gates, and a website copy pass
that held back three claims which would have been false on the day they
shipped.

client from a public CDN at the floating tag @2, with no integrity
attribute, and their content security policy named that origin. That
script holds the session token and mediates every read and write. A single
malicious publish to the 2.x line would have run with full session
authority against every customer at once. It was found by an external
advisor's audit and confirmed here before anything was changed.

The detail worth keeping: app/vendor/ already held a vendored PDF worker,
pinned and same-origin, with a comment explaining that a cross-origin
worker will not start. The harder case had been reasoned through. The
easier and more dangerous one was missed because nothing checked it.

The client is now vendored at exactly 2.112.1, with the version in the
filename so an upgrade is a visible diff, pinned by SHA-384, served from
our own origin. script-src is 'self' on all three pages. Ten further pages
that carried no policy now carry one, and both verification pages keep
connect-src 'none', which is what lets a reviewer prove they make no
network request.

tools/supply-chain-gate.mjs makes it permanent and was proven both ways
before shipping: reintroducing the CDN tag fails it, and appending one
byte to the vendored client fails it.

The same audit found that the claims gate and the copy gate were never in

Published numbers are now bound to what the suites prove.

### The design pass

Two visual defects, both measured on the live pages rather than judged by
eye.

The nav's primary button rendered slate text on blue at a contrast ratio of
2.12 to 1, where WCAG AA requires 4.5. The button rule was correct. The nav
rule beat it: `.site-head .links a` has specificity (0,2,1) against
`.btn-primary` at (0,1,0), so every primary button inside a nav quietly lost
its white text. Fixed with `:not(.btn)`, and the reason is written beside the
rule.

Body text had no measure. A paragraph took whatever width its parent grid
gave it, which produced 95-character lines on the homepage and 90 on the
verify page, while leaving up to 360 pixels of dead gutter on the right. Both
complaints are the same defect: too long to read and too narrow to look
deliberate, at the same time. There is now one measure for the site, 66
characters with a 74-character wide variant, applied through a prose column
that centres so the leftover space sits evenly on both sides.

tools/design-gate.mjs keeps both. It computes contrast from the colour
tokens, refuses any button rule that paints a background without setting a
text colour, refuses an unqualified nav link rule, and requires the measure to
exist and to stay inside the readable range. Proven by reintroducing the
specificity collision and watching it fail.

## 2.57.2 · C1 hardening: token boundary, agent fuzz, injection, egress

Freeze release. No features. One high-severity fix, three completed
adversarial sweeps, and one residual named rather than hidden.

C1-004, high: endpoint_create required https and nothing else, so any
project manager could point a webhook at loopback, RFC 1918 space,
carrier-grade NAT, an IPv6 form, or the cloud metadata address, and make
the service-role delivery worker sign and POST to it. A signed request to
an internal listener is worse than an unsigned one. migrations/0029_ssrf_guard.sql
adds one place that decides whether ReqPub sends bytes anywhere, applied
at creation and again at dispatch so a row stored earlier never receives
bytes either. It refuses IP literals in decimal, hexadecimal, octal,
dotted and bracketed IPv6 forms, userinfo in the authority, internal
suffixes, single-label names, and trailing-dot forms, and it names the
reason. Verified on production against all of them.

C1-005, medium, accepted with a stated residual: a name that resolves
publicly at creation and privately at delivery defeats any name-based
guard. Closing it needs address pinning inside the delivery function.
Redirects are already not followed, which closes the other half.

C1.2, the token boundary: five token types, twenty cross pairs, every one
refused. A revoked token is byte-indistinguishable from one that never
existed. No token value and no signer address appears in any token-scoped
response.

C1.4, the agent surface: malformed envelopes, wrong types, a two-megabyte
parameter, two-hundred-deep nesting, unknown methods and tools, scope
escalation against foreign ids, propose with the gate off, and nine
authorization header shapes. Every response is scanned for keys, tokens,
addresses, stack frames, paths, SQL fragments, and database internals. A
foreign-project refusal is indistinguishable from a not-found refusal, so
the endpoint is not an enumeration oracle.

C1.8, injection and rendering: seventeen hostile strings written through
the real RPC and read back through the real escapers and CSV writer.
Values cross a parameter boundary and round-trip byte for byte; no
payload forms a tag after escaping; every formula-leading value is
prefixed; a NUL byte is refused at the database boundary rather than
truncating.

C1.6 storage probing and C1.7 parallel rate limits remain open and are
named as open in docs/security/HARDENING_REPORT.md.

Deploy: run supabase/migrations/0029_ssrf_guard.sql once, after
migrations/0028_authz_lockdown.sql. Already applied to production.

## 2.57.1 · C1 hardening: authorization lockdown

Freeze release. No features; one critical security fix and the permanent
suite that keeps it fixed.

PostgreSQL grants EXECUTE on every new function to PUBLIC, and PUBLIC
includes the anon role every browser client holds. ReqPub's public API
functions were individually revoked and re-granted, but its internal
helpers never were, because they are only ever called from inside other
definer functions and carry no authorization checks of their own.
Eighty-six definer functions were reachable by anon. One of them,
log_activity, writes directly to the activity trail and swallows
exceptions by design.

Demonstrated, not theorized: as anon, with no session and no membership,
a caller could insert a forged approval into any organization's trail,
and the insert trigger chained it as a genuine event with no error
returned. This is finding C1-001, critical, and it defeated the product's
central claim.

migrations/0028_authz_lockdown.sql revokes execute on every function in the public
schema from PUBLIC, anon, and authenticated, then grants back exactly the
surface the codebase already declared. log_activity also gained two
guards: it refuses an organization that does not exist and a project that
does not belong to the organization named. On production the anon surface
fell from 86 functions to 17, the exploit is refused, and no trail row
moved.

Two self-inflicted findings are recorded in the same report rather than
quietly fixed: the first lockdown revoked the five membership predicates
that RLS policies call, breaking every policy-protected read until the
backend suites caught it; and my_context() had never been granted
explicitly, so it broke on production until the whole client surface was
checked live rather than sampled.

tests/backend-e2e/authz-matrix.test.mjs reproduces the exploit on an
unpatched stack, proves the fix, and pins the reachable surface to a
committed allowlist, regenerating docs/security/AUTHZ_MATRIX.md so drift shows up in
review. A measured negative result is recorded too: ALTER DEFAULT
PRIVILEGES does not make new functions private on this PostgreSQL, so the
suite is the control, not the default.

Deploy: run supabase/migrations/0028_authz_lockdown.sql once, after
migrations/0027_pursuit_lineage.sql. Already applied to production.

## 2.57.0 · The Record of Delivery and the receiver templates

An engagement now closes with a document a client can read. The Record of
Delivery states the objective and success metrics as they were authored,
the baseline sequence with labels, dates, statuses, and authors, what
changed between consecutive approved baselines exactly as the diff
reports it, the accepted thresholds with their named eval sets and who
executed them, every signature with what sealing proved in the

exists, and instructions for checking all of it without ReqPub and

What it does not contain is the point. No status, no score, no health, no

says so plainly: no objective stated, no prior approved baseline to
compare against, no signature captured, not sealed. A reader who wants to
know whether the engagement went well reads the facts and decides. The
closing line says as much, and the tests refuse any sentence that would
imply otherwise.

A second action downloads the close package: the Record of Delivery plus
the entire evidence pack, flattened into one archive under a single
manifest, because two manifests describing one archive is an invitation
to check the wrong one. Practice watermarks like everything else, and no
token or email address reaches either artifact.

For integrators, templates/receivers/ ships two runnable references on
platform builtins only, one for a service you run and one for any

delivery accepted, one altered byte refused, a stale timestamp refused
before parsing, an unknown key refused without fallback, and a repeated
deliveryId refused while still answering 2xx. docs/RECEIVERS.md states
the field mapping normatively, field by field, with the idempotency rule,
the retry ladder, and a security checklist in MUST and MUST NOT terms. No
product, platform, or firm is named anywhere in the directory or the

## 2.56.0 · Pursuit Mode and engagement lineage

A pursuit is the scope conversation before there is an engagement. Set
the pursuit control at creation, or start from the Pursuit template, and
the worksheet trims to the sections a scope conversation actually has:
objective and context, success metrics, scope and approach, assumptions
and dependencies, stakeholders. The trim rides the same per-section
condition mechanism the engagement toggle has used since v2.20, so a
non-pursuit record renders exactly as it did before, pinned by test. The
record opens on the Document tab, and a three-step header states three
facts it already holds: baselines captured, whether a share exists,
whether a signature exists. Facts, not progress scoring; nothing is
predicted and nothing is ranked.

Once a pursuit baseline is signed, one action promotes it. Promote
recomputes the baseline fingerprint through core.js and asserts it equals
what the signer actually signed; a mismatch aborts with a plain error and
writes nothing. On a match it creates a new engagement record, carries
the authored content across through the same rev-checked, additive,
sequential discipline every template start uses, and records the lineage.
Practice inherits, the single deliberate exception to nothing-is-
inherited: a rehearsal's child is a rehearsal.

Lineage is three additive nullable columns and one set-once definer RPC.
A manager on the child sets it once; a second attempt is refused rather
than silently overwritten, because a citation that can be rewritten is
not a citation. The write validates the fingerprint format, logs
lineage.set, and rides the activity chain. Engagements descending from
records outside promote can cite them the same way. The cover carries one
quiet Born from line with the reference and the first twelve characters
of the fingerprint. Nothing is inherited, computed, or propagated across
the link.

Deploy: run supabase/migrations/0027_pursuit_lineage.sql once after
migrations/0026_book_practice.sql; push; hard refresh.

## 2.35.0 · independent verification, executed-by, and the weekly update dashboard

Three additions and one small hardening, each carrying its reasoning.

**Independent verification.** A baseline now exports as a verification
bundle: one JSON file holding exactly what the fingerprint covers (label,
seq, snapshot) plus the recorded fingerprint. Three consumers, one recipe.
The public page (verify.html, linked in the site nav and footer)
recomputes the SHA-256 fully in the visitor's browser and compares;
nothing is uploaded. It imports the same canonicalJson and sha256Hex from

unusable input or nothing to compare, and --print-canonical writes the

## 2.34.2 · security: the update panel leaked signing credentials

A defect introduced in 2.34.0 and found in an audit of that release. If
you deployed 2.34.0 or 2.34.1, deploy this.

**What was wrong.** update_context returned the sign token for every
signature request on the baseline. A sign token is not a reference, it
is the credential: sign_request_sign() takes a token and a typed name,
is granted to anon, and asks for nothing else. So possession of a weekly
update link - a low-sensitivity artifact meant to be read and forwarded
around a client organization - was the power to forge every signature on
the acceptance baseline, each one landing as a real approval row with
the correct role and an activity entry naming the signer. On a product
whose entire claim is that the record proves who agreed to what, that is
the worst reachable defect, and it was mine.

**The fix.** A sign token is now released only to the person the update
was addressed to, matched on email. The panel therefore grants nobody
anything they were not already sent directly, which is the correct
boundary: your own link, and nobody else's. Every other signer still
appears with name, role, and status, so the panel stays useful, but with
no link and no live token. signer_email is no longer returned at all;
the panel needs a name and a role to read well, not the mailbox of
everyone who signed. An update issued to no recipient releases no tokens
at all.

Six backend checks pin it, including the attack stated directly: hold
the update link, try to sign as the client sponsor, and fail because the
credential is not in the payload.

Checks: 231 unit, 405 backend. Deploy: run supabase/migrations/0018_updates.sql, or
re-run schema.sql. Then push and hard-refresh.

## 2.28.0 · tables are the document

Intake could read a PRD's prose and lose its substance. A consulting-grade
requirements document is mostly tables, and the extractor read PDFs as
text lines only: statement and fit-criterion cells interleaved as bare
lines, and the priority cells ("M M1 T") landed as standalone lines the
segmenter mistook for ALLCAPS headings, shattering one real 16-page PRD
into 98 junk segments. Word documents failed the same way from a different
cause: mammoth's markdown writer flattens tables into bare paragraphs.
Reproduced against a real table-built PRD: 9 placements, mostly junk (1
garbage functional-requirement row against 60 real ones), 98 unplaced
fragments. This release makes tables first-class in both formats. Same
file after: 60 of 60 functional requirements with their permanent IDs,
real fit criteria, and expanded priorities; 21 NFRs; 5 evaluation rows;
9 metrics; 9 assumptions; 9 personas; 9 interfaces; 15 glossary terms;
goals, releases, and decisions; unplaced down to 5 honest blocks.

- **A geometry engine rebuilds PDF tables deterministically**
  (pdfMarkdownFromItems in intake.js). pdf.js reports the exact x and y of
  every text fragment. Fragments cluster into visual lines by y; recurring
  x positions are the columns; a new logical row begins when the leftmost
  column receives text and the vertical rhythm agrees (line spacing inside
  a row is the smallest gap in the region, so a wrapped ID cell like
  "EVAL-M2-0" / "1" never starts a false row); wrapped cells merge into
  their columns. Detected tables emit as markdown pipe tables - the
  mapper's native form - and everything else stays prose. Running headers
  and footers (same short line on most pages, digits normalized) are
  dropped. Four or more aligned fragments on one line are tabular on
  sight, which is how a one-row stub left by a page break survives.
  Items without coordinates degrade to the old line join exactly, so the
  function is a strict superset of the v2.26.1 behavior. Pure, no
  network, no model calls, fully unit-pinned.
- **Headerless tables are read by content** (inferColumns). Some PDFs draw
  the header row as one text run the geometry cannot split, so the first
  data row lands as the markdown header. Content identifies the columns:
  an ID column is IDs, a MoSCoW column is single letters, and of the
  remaining wide columns the left one is the statement and the right one
  the fit criterion. When the header row itself is data, it is restored
  as a row from the raw uncased cells. IDs wrapped by a narrow cell are
  recognized and normalized de-spaced ("EVAL-M2-0 1" lands as
  EVAL-M2-01), which also keeps a Rel column ("M2") from stealing the id
  role.
- **Extraction is table-first for every rows target.** fr, nfr, eval,
  metrics, glossary, persona, interfaces, gates, and the new decisions
  target read every pipe table in their section - named headers when
  present, inferred columns when not. The source's permanent IDs ride as
  a prefix on the primary text (FR-M1-001: ...), because identifiers are
  doctrine and must survive intake. MoSCoW letters expand (M, S, C, W
  become Must, Should, Could, Won't). List-shaped sections (goals,
  assumptions) accept tables too, one line per row with the ID kept and a
  Label column carried in parens. Columns the record has no home for
  (Rel, Ver) are dropped; the uploaded document stays their source of
  truth. The old whole-body fallback that turned a section's intro prose
  into one junk row is removed: a rows section with neither bullets nor
  tables contributes nothing, honestly.
- **Structure mapping got three corrections.** Two-level numbered
  headings (7.1, 7.4) segment with their depth and number; a numbered
  subsection whose number proves the nesting inherits a rows-shaped
  parent no matter what its own title says ("7.4 ... the CI gate" inside
  Functional Requirements is functional requirements, not stage gates),
  while under a long-form parent a subsection speaks for itself (1.1
  Goals classifies as goals) and an unknown title stays unplaced -
  unplaced beats misplaced. The ALLCAPS heading rule now requires a real
  word of three letters, so a stray "M M1 T" line can never split a
  document again. New classifications: Users lands in personas, Releases
  in gates, Decisions in the decisions rows, and Data/Privacy/
  Safeguarding sections land in NFRs, where privacy requirements belong.
- **Word documents keep their tables** (htmlToIntakeMd). The docx path
  now converts through mammoth's HTML, which preserves tables, and a
  bounded pure walker turns that HTML into the segmenter's markdown:
  tables become pipe tables, headings become #-headings, list items
  become bullets, entities decode once at the end. mdUnescape stays
  exported and tested; the docx path no longer needs it.
- **Pinned against the document that exposed the failure.** 15 new unit
  checks (41 intake total, 207 suite-wide), including a fixture of real
  page geometry frozen verbatim from the table-built PRD's assumptions
  page: the engine must rebuild that exact table, wrapped statement and
  label cells merged, IDs and labels intact, forever.

Known limits, stated plainly: a table split across a page break relies on
the per-page repeated header plus one-row stub recovery (the Collection
Ventures template repeats headers, so it round-trips); a mid-word wrap in
a narrow cell keeps its space ("Demonstra tion") - cosmetic, and in this
template confined to a dropped column; user-story prose between a rows
section's tables is not row data and is not imported. Deploy is a
frontend push only - no schema change.

## 2.8.4 · fix replies doubling in the conversation log

- Fix: a team reply in the inbox appeared twice (identical, both "just now").
  Cause was a realtime race - the websocket echo of the inserted message often
  arrives before the HTTP insert response resolves, and the optimistic local
  add was not deduplicated, so the same message was appended twice.
- All message adds (optimistic and realtime) now go through one shared
  pushUnique helper that adds by id only if absent, so a reply lands exactly
  once no matter which path wins the race. New unit test covers both orderings,
  repeated echoes, and distinct messages that happen to share text (5 checks).

## 2.1.0 · hardening release

Security

- Fixed a cross-org share overwrite: `share_put` now fences its conflict path
  to the caller's own org and project, so a colliding or guessed token
  belonging to another workspace is refused instead of updated.
- Rate limits on all anonymous endpoints: SME submissions (60/hour per project
  per origin), request intake (30/hour per request), SME thread replies
  (30/hour per thread).
- Realtime send (presence, client broadcast) restricted to org members;
  partners now receive only. Database writes were never possible via realtime.
- Team author identity on messages and team notes is stamped server-side from
  the signed-in profile; client-supplied names are ignored for team entries.
- Size ceilings: 256 KB per worksheet answer, 128 KB per row (enforced in the
  RPCs), 20 KB per comm/message body (CHECK constraints on new writes).

Correctness and resilience

- `durable()` no longer retries definitive PostgREST errors (permission,
  constraint, missing function); retries are reserved for genuine network
  failures. Permission errors now surface immediately instead of after 2.5s.
- Render errors show a recovery screen instead of a blank page.
- Session expiry or sign-out in another tab returns the app to the login page.
- New index `comms(org_id, created_at)` for dashboard rollups.
- `verify.sql` now also checks broadcast availability, identity triggers, and
  size constraints.

Project hygiene

- LICENSE (proprietary), SECURITY.md, CHANGELOG.md, CI workflow running the
  domain and concurrency suites on every push.
- Backend e2e extended: cross-org token takeover attempt, anonymous rate-limit
  trip, server-stamped team identity, oversize-payload rejection, and
  viewer-role RLS checks executed under the `authenticated` role.
- Accessibility: dialogs carry `role="dialog"` and `aria-modal`; the command
  palette input is labeled.
