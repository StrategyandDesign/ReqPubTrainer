# RELEASE REPORT v2.55: The Book, the invoice packet, and practice mode

The largest release of Phase A: the projects grid becomes the Book, any
sealed signature yields an invoice packet, and practice mode makes
rehearsal structurally incapable of becoming evidence.

## What shipped

The Book. Cards carry pending and signed counts and a Sealed chip from
one batched member-scoped RPC, project_acceptance_facts; a missing fact
renders nothing and the layout never bends. Export book, manager only,
writes one row per signature across the caller's records in the frozen
evidence.csv columns plus engagement_value, practice excluded at the
RPC. Chain columns carry each receipt's at-seal snapshot where sealed
and the current chain tail otherwise: recorded facts, never a fresh
verdict. Engagement value is authored text through the same rev-checked
ctrl-field mechanism as the propose gate, rendered on the Share page and
in that one column, never parsed, never summed, never computed upon.

The invoice packet. From any sealed signature: receipt.json, the
signature line, both .tsr files present, one evidence row, a printable
cover stating exactly what the packet is, and a manifest hashing every
file with its own canonical hash. On demand, stored nowhere,
deterministic except the manifest's generatedAt, proven by test.

Practice mode. The column defaults false and is settable only at
creation, from the checkbox or the Practice engagement template start; a
guard trigger raises on any change in either direction. Watermarks: the
worksheet header, every cover through coverHTML, the brief and share
pages and SME surfaces through the brandBanner chokepoint which no
longer depends on a logo, both return paths of the sign page and
archive, every export, and both bundle formats, additively, so every
artifact produced before this release is byte-unchanged; both published
schemas gain the optional constant-true field and the SPEC tables the
matching rows, parity enforced. A practice project produces zero webhook
delivery rows ever, proven against a live enqueue on its evidence
sibling. The seal states practice inside the receipt itself. A craft
shelf topic carries the sample intake for a training run.

## Recorded adaptations

Three spec lines met the codebase honestly. evidence_gather's practice
refusal shipped in v2.52 and is live; this release pins it rather than
replacing a correct function. Project creation is a direct RLS insert,
not an RPC, so practice rides the insert and the trigger carries the
immutability; the evidence backend suite now creates its rehearsal at
birth for the same reason. The mcp function's practice flag has ridden
its RPC layer since v2.51; the redeploy brings serverInfo to 2.55.0.

## Production deploy, executed and verified

migrations/0026_book_practice.sql ran clean in the SQL editor. Verified live, not
assumed: the practice column exists, project_acceptance_facts and
book_export both resolve, get_share answers, and the immutability
trigger is armed, proven by attempting a real flip on a live project and
receiving the refusal in the function's own words.

Both edge functions redeployed from their paste files and confirmed by
the functions list: mcp at version 2, seal-receipt at version 7, both
ACTIVE, both verify_jwt false, all eight functions ACTIVE. Each payload
was verified byte-exact in the browser before deploy, matching length
and SHA-256 against the file on disk.

Technique recorded for future deploys: gzip the paste, base64 the
compressed bytes, and let the browser decompress through
DecompressionStream. That cut the mcp transfer from nine slices to three
and the seal transfer from ten to three. Dashboard tokens expire within
minutes, so the token must be re-read from localStorage immediately
before each management API call, and a tab reload is the reliable way to
force a fresh one. reqpub.com serves the whole repo tree over HTTPS but
without CORS headers, so the dashboard origin cannot fetch paste files
directly.
