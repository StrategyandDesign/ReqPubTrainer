# RELEASE REPORT v3.1: The record conformance release

A discovery method paper, Product Discovery with Agents, describes the
record this product keeps. Sixty four of its sentences were checked against
this codebase, each with a file and a test or a named search behind it:
thirteen verified, thirty six delivered in a narrower shape, nine missing,
four contradicted, two already called future by the paper. This release
closes the contradictions and the narrow shapes a client's control function
would test first. The rest is on the gap list that came out of the audit.

## What a signature now covers

A signature page carried each requirement's statement and stripped its fit
criterion by doctrine, so a signer confirmed a fingerprint over text they
could not see. The signature page and the printed client baseline report now
carry fit and executed-by. A brief for an SME, and the presentation link built
from it, are unchanged: that reader is reviewing scope, not attesting to a
pass condition. The decision lives in one function, buildSharePayload, and a
test pins both shapes.

## Who may approve

An approval slot with no assigned teammate belongs to someone outside the
team. approval_decide refuses to approve it with esign_required, and the
provenance trigger refuses the same transition on a direct write, so neither
the RPC nor a manager with table access can satisfy a client's slot.
sign_request_sign lands on the slot named for the signer, or opens one, and
advances the version exactly as an in-app decision does; a fully signed
version no longer stands In review. The manager-recorded sign-off on an
approved baseline is gone, and the panel says what replaces it.

## What the seal covers

Readiness signals were computed at generation and frozen into the version
snapshot, under the fingerprint the client signs, then printed as Record
state on the client cover. The snapshot now carries answers, sections, the
gate name and the walkthrough, and nothing derived. The gate packet computes
its criteria state at print time and says so on the page.

## Timestamps, checked and read

receipt_tsa_update accepted any text from a token holder or a project member
and marked the receipt dual. It now refuses a reply without the shape of a
granted RFC 3161 response carrying this receipt's canonical hash (a DER
sequence, PKIStatus granted, the hash bytes present), and a stored reply is
write-once, so a sign-link holder cannot swap a genuine token for one that
merely passes the shape check. The verify CLI reads each token on node
builtins: status, message imprint equal to the receipt hash, genTime, the
message-digest attribute against the TSTInfo, and the CMS signature against
the certificate inside the token, RSA PKCS#1 and ECDSA with SHA-256, 384 or
512. A token the tool cannot read is reported as not checked, with the
openssl line, and does not fail the receipt. The chain from the certificate
to a root is the reader's trust decision, and the openssl command for it is
printed as before. A synthetic authority under tests/fixtures signs real tokens for the
suites, since the public authorities are not reachable from a runner and a
recorded response would pin one vendor's encoding.

## Authorship on rows

field_rows carries author_name and origin, stamped once at insert by
upsert_row. A row promoted from an Inbox entry passes that entry as its
source and the server copies the author and origin from it; a row typed in
the app is authored by the manager who typed it. Editing a row later keeps
both. The assembled answers carry them as _author and _origin beside the
attested recorder, so a baseline keeps its authors after the people move
on, and requirements.json prints them. The Inbox labels agent proposals as
Agent.

## EARS, prior signers, defects

A requirement outside the five EARS shapes raises a readiness warning that
names the shape to write; the placeholder, the starter template and the help
topic use it. A version with no signature requests offers the people who
signed the previous signed baseline, one click for all of them. Three defects
the audit found are fixed: the Record of Delivery's timestamp vocabulary, the
eval set missing from the diff columns, and the fingerprint absent from two
package files and truncated in a third.

## Gates

Migration 0030_record_conformance.sql, idempotent, with its ledger row; the
replay proof holds schema.sql and the thirty migrations to one database.
Every backend suite that replays an older migration now ends its stack with
0030, so what the suites test is what ships. Audit clean, capabilities gate
clean at 45 entries, schema parity clean, eslint at zero errors. New checks
in both chains; the recorded counts in tests/COUNTS.json are the ones the
suites produced on this release.

## Deploy

Apply 0030_record_conformance.sql to the project database first, then
deploy the site from main: the app selects the two new field_rows columns on
every project load, so a site deployed before the migration fails to open a
project. The migration adds two columns, adds one function, replaces five
functions and one trigger, and backfills nothing. The seal-receipt and mcp
edge function sources change only in their APP_VERSION stamp; without a
redeploy the MCP server keeps advertising 3.0.1, which is cosmetic. Existing
receipts keep their stored timestamp status; the verify CLI will now read
their tokens.

## Left open

The ranking object, row level threads and decisions, the clearance section,
findings and exits, the full export, the white label switch, and the test
input and grader columns are on the gap list from the audit and are not in
this release.
