# RELEASE REPORT v2.57: The Record of Delivery and the receiver templates

The last feature release of Phase A. An engagement can now close with a
document a client reads, and an integrator can now wire ReqPub into their
own system from a normative spec and a runnable reference.

## The Record of Delivery

Assembled from the record and nothing else: the objective and success
metrics as authored, the baseline sequence with labels, dates, statuses,
and authors, the per-column changes between consecutive approved
baselines exactly as reqDiffDetail reports them, the accepted thresholds
with named eval sets and executed-by, every signature with what sealing
proved stated in VERIFY.md's own words, the Born from citation where
lineage exists, and verification instructions pointing at the published
recipe and the offline checker.

What it refuses to contain is the point. No status, no score, no health,
no progress, no summary the record did not author. The empty states are
where that discipline shows: no objective stated, no prior approved
baseline to compare against, no signature captured, not sealed. A
signature without a receipt says not sealed rather than implying one. The
receipt hash prints as a prefix, never in full. The closing line states
that ReqPub asserts no judgment about the work, and a test refuses any
sentence that would imply otherwise.

The close package flattens the Record of Delivery and the entire evidence
pack into one archive under a single manifest. The pack's own manifest is
replaced rather than duplicated, because two manifests describing one
archive is an invitation to check the wrong one. Deterministic except the
moment recorded in the manifest, practice-watermarked like everything
else, and free of tokens and addresses by grep.

## The receiver templates

templates/receivers/ ships two references on platform builtins only:
node-receiver.mjs for a service you run and serverless-handler.mjs for
any runtime that hands you a Request. Both enforce the same load-bearing
order: skew, signature, parse, dedupe, hand off. Parsing before verifying
means acting on bytes an attacker chose; deduping after handoff means
doing the work twice.

../RECEIVERS.md states the mapping normatively, every payload field to
a target record field with a MUST or SHOULD rule, plus the idempotency
rule, the retry ladder, and a security checklist in MUST and MUST NOT
terms. No product, platform, or firm is named anywhere in the directory
or the document, and a test enforces the neutrality against a list of
twenty names.

## Gates

Audit clean, capabilities gate clean at 39 entries, schema parity clean.
Unit chain green with 38 new checks, including six against real Ed25519:
valid accepted, one byte altered refused, stale timestamp refused before
parsing, unknown key refused without fallback, signed non-JSON refused
after the signature passes, and a repeated deliveryId refused. Backend
718 checks across 28 suites, exit 0, untouched by this release and run
anyway.

The spec said no schema change was expected. Confirmed rather than
assumed: schema.sql is byte-identical to v2.56 and no new migration file
exists.
