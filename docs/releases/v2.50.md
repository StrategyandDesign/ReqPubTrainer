# Release report - v2.50.0, signed webhooks

## What shipped

The record now announces itself, on the customer's terms. A manager adds an
https endpoint on the Access page; four events then post one signed JSON
delivery per active endpoint: sign.signed, sign.declined, seal.issued, and
seal.timestamped. With zero endpoints configured the feature does not
exist: nothing enqueued, nothing sent, every prior flow byte-identical
except an empty pendingDeliveries list on the two sign functions.

Signing is platform-level Ed25519 under whk-1: X-ReqPub-Key-Id,
X-ReqPub-Timestamp, X-ReqPub-Signature over utf8(timestamp + "." + body).
Receivers verify against reqpub-keys.json and reject skew over 300 seconds;
../WEBHOOKS.md is the receiver contract and includes a working Node
verifier. The whk-1 pair has been part of scripts/generate-seal-keys.mjs
output since v2.48, so an operator who ran the key step then has nothing
new to generate.

The payload carries the record, never the secrets: project, version label
and seq, sign request id, receipt id on seal events, document fingerprint,
chain head seq and link hash, signer name and role, occurredAt. Never a
token, never an email address, never document content. The chained audit
line for every endpoint change records the host only, so a credentialed
query string in an endpoint URL can never leak into org-visible activity.

Delivery is a new deliver-webhooks function: one delivery per call, 10
second timeout, redirects refused, and an SSRF guard that resolves every
host and refuses loopback, RFC 1918, link-local and metadata, CGNAT, ULA,
and v4-mapped forms, for A and AAAA answers alike. Failures walk 1m, 5m,
30m, 2h, 12h, then dead. U1 (pg_net) stays unconsumed, so dispatch is lazy
plus manual, and the fix file header says so: the signer page pings the
deliveries its signature created (the sign functions return the ids as
unguessable capability handles), the seal flow sweeps afterwards, and the
manager panel carries Redeliver and Deliver pending. Enqueue rides
non-blocking AFTER triggers; a webhook problem can never break a signature
or a seal.

## What the tree fought about

The harness has no service_role role, so the two engine grants
(webhook_delivery_take, webhook_delivery_result) are wrapped in the same
role-exists guard v2.49 uses; production grants land, the embedded suite
applies clean twice. Node 22 type-strips .ts imports, so
deliver-webhooks/index.ts is written annotation-free with its dependency
loaded inside the Deno branch: the unit suite imports the exact shipped
file and drives the real classifier, the real signing, and the real handler
with a verifying receiver, rather than testing a copy. receipt_tsa_update's
second parameter is the signer token, not a status; the suite passes ''
like the sealing suite does and lets the DER arguments drive single and
dual.

1. Supabase SQL editor: run supabase/migrations/0023_webhooks.sql (migrations/0022_attachment_hash.sql
   must already be applied).
2. Dashboard, Edge Functions: create deliver-webhooks, paste
   supabase/functions/deliver-webhooks/index.ts verbatim, Verify JWT OFF.
3. Secrets: WEBHOOK_SIGNING_KEY, from the scripts/generate-seal-keys.mjs
   run you did in v2.48. If you skipped it then, run the script now and
   complete all four of its steps (both secrets, reqpub-keys.json, the
   receipt_keys rows, the timestamp).
4. Push the repo, hard refresh, footer 2.50.0.
5. Nothing else changes until a manager adds an endpoint.
